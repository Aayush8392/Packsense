# P2 — Lakehouse

Turns landed files into queryable layers on Databricks: bronze (raw, append-only), then silver (typed, checked, scrubbed).

| File | What it does |
|---|---|
| `notebooks/bronze_load.py` | Loads landed delta files into `workspace.packsense_bronze.bronze_delta_raw`. Idempotent: insert-only MERGE on `(code, last_modified_t)`, a manifest row written last, and a row-count check against the capture manifest. |
| `notebooks/silver_load.py` | Bronze -> silver, per finished bronze file: silver rows, quarantine rows (broken records only), a hand-off check, then the manifest row. Idempotent and order-independent (every record is handled on its own); runs as the second task of the job (even if bronze ended red); pings healthchecks `packsense-core`. The decisions live in `silver_lib/`; the notebook only does the Spark reads and writes. |
| `silver_lib/run.py` | Processes one batch of bronze rows (each record on its own, so no file or row order can change a result), returning silver rows, quarantine rows and the run counters. Pure Python, tested on real records. |
| `bootstrap/create_bronze_job.py` | **Superseded** by the Asset Bundle (`databricks.yml`, `p3_delivery/resources/bronze_job.yml`); it is kept only until the old admin-owned job is deleted after the new job's first scheduled run, then it is removed. It created the bronze schema and the job (`create`, `run`, `schedule`, `status`). The job has three tasks, bronze, then silver (runs even if bronze ended red), then the drift check; the bundle-owned job runs a deployed copy, not `main`. |
| `bootstrap/create_hmac_key.py` | Creates the HMAC key that scrambles contributor usernames in silver and stores it in secret scope `packsense` (`hmac_key_v1`). The key is generated in memory and never printed or written to disk; there is no escrow copy (if lost: new key, silver rebuilt from bronze, every contributor gets a new code; steps in [`docs/runbook-rekey-hmac.md`](../docs/runbook-rekey-hmac.md), drilled once on scratch, 2026-10-16: `bootstrap/rekey_drill.py`). `create`, `check`, `dry-run`, and `put-secret` (stores another secret, such as a healthchecks ping URL, from a hidden prompt; refuses to touch the HMAC key). |
| `contracts/silver.yml` | The silver data contract, version 4: the allowlist of 81 columns (everything else is dropped), the scrub patterns, shape checks, own-handle redaction, the egress rules and quarantine codes. Read by the code; changing a column means changing this file. |
| `notebooks/seed_dump_load.py`, `seed_lib.py`, `bootstrap/run_seed_load.py` | The India seed from OFF's full dump (one gzip stream held as 13 parts in the private archive): `stage` reads it once and keeps the India lines (`countries_tags` contains `en:india`), checking every part against its recorded sha256; `promote` copies the staged lines into bronze (refuses unless silver's contract is v3); `drop_stage` cleans up. Done once on 2026-10-15: 24,795 India products, 22,342 of them new to bronze. |
| `bootstrap/silver_v4_check.py` | Scratch rebuild of silver from ALL of production bronze with the real key, compared with production: balance, keys, every old column row for row, each new column counted against bronze's raw JSON, residue in the tag columns, lineage; `drift` replays the drift monitor on the result. Production is only read; scratch schemas are dropped by `cleanup`. Used to prove v4 before any production change. |
| `silver_lib/drift.py`, `notebooks/drift_check.py` | The schema-drift monitor: after silver, judges each new daily file (share of products with a value for each of 69 contract columns, the nutrition-format mix, volume, `schema_version`) against the last 30 days, and reports field-name families never seen before. Findings go to `silver_drift_report`; an alert turns its own healthchecks check red and never fails the data load. |
| `silver_lib/` | The silver logic as plain Python, unit-tested without Spark: `contract.py` (load/validate v4), `personal.py` (HMAC, scrub, own-handle redaction, fingerprint, quantity parsing, shape checks), `transform.py` (raw record -> silver row or coded quarantine row, including the legacy-nutriments mapper), `schema.py` (table definitions generated from the contract), `egress.py` (the one exit function every export path calls). |
| `tests/` | `python -m pytest p2_lakehouse/tests` from the repo root. Fixtures are real bronze records, sanitised (see `tests/fixtures/README.md`). |
| `bootstrap/extract_fixtures.py` | Regenerates the fixtures inside Databricks (names never leave it). |
| `bootstrap/crash_test.py` | The real mid-write kill test (`setup`, `bronze`, `silver`, `window`, `cleanup`): copies 6 real delta files into a scratch landing folder, cancels a running scratch run while it writes, re-runs it and compares with production; production tables are only read, and `cleanup` checks their counts are unchanged. Takes the Databricks host and token from the environment (or `--env-file`). |

## Limits of the silver layer (measured on the data in this repository's pipeline)
- **Personal data.** Silver validates and transforms; it does not detect and block. Free text is down to `product_name` and `brands`; the claim is a measured bound (see the top-level README), not a guarantee. `ingredients_text` is not kept, only a fingerprint (it held 99.6% of the contact-shaped text). Hashed contributor codes are marked `egress: never` and are protection against our own readers only.
- **The exit function is built and unit-tested, but wired into nothing yet.** No export exists yet (release, site, LLM prompts); the test that fails when an export path skips it is to be added with the first one.
- **Legacy nutrition (old OFF format).** Only `<nutrient>_100g` keys of an allowlist are read; OFF's computed keys (`nova-group`, fruit and vegetable estimates) are ignored, so a product with only those stays `none` (1,231 India products). The per-100 g or 100 ml basis is not recorded in the old format (`nutrition_per` is NULL) and there is no per-source breakdown (`input_sets` NULL), so these rows are excluded from source-disagreement work. 91,915 rows were written under contract v2; 2 of them are old-format products that stayed `none` (not reprocessed, by decision).
- **107 India products** carry per-source sets but no aggregated set; silver labels them `none` while still keeping their `input_sets`.
- **Quarantine** is for broken records only (2 rows, both the empty barcode). Implausible values are kept on purpose: they are the signal the triage work looks for.
- **The drift monitor** watches presence and shape from a 14-day baseline, so its 5-point margin is a judgement call that tightens as history grows; it cannot see a change of meaning or unit. It also watches how often the shape checks change a value (dropped tags, values that fail their type, dropped nutrient entries, nulled enums): each delta day is re-run through the silver transform in memory and only counts are stored (`silver_drift_metrics`). On the 15 real days only tag drops ever occurred, and one day (a producer-heavy import) had 7.04 dropped allergen tags per 100 products against 0.31 to 1.51 on the others, which is the one alert it raised. The rate rule (3 times the highest recent day, at least 0.5 points and 15 products above it) is a judgement call from those 15 days, and a spike stays in the 30-day baseline, so a repeat of the same size within 30 days would not alert.
- **Crash recovery is proven by real kills, with limits** (2026-10-15, `bootstrap/crash_test.py`). A running scratch copy of each notebook was cancelled through the Jobs API while it wrote, then re-run, and the result was compared with production for the same 6 real delta files (identical content, no duplicate keys, one manifest row per file). Bronze: 2 kills landed after a file's data was merged but before its manifest row was written, and both recovered; a third trial's kill landed after the run had finished and does not count. Silver: 1 kill landed after a file's silver rows were written but before its manifest row, and 2 landed between files; all recovered. Limits: a cancel takes about 30-37 s to take effect, so the exact moment of a kill cannot be chosen (the two bronze risky-window kills left the same state, so they are closer to one observation than two); the first 6 files had no quarantined rows, so the step between the silver write and the quarantine write was exercised separately (below); only a cancelled run was tested, not a lost node or a network cut. A file recovered this way gets a manifest row with `rows_inserted = 0`, because its rows were already there.
- **Crash recovery with quarantined rows** (2026-10-16, `crash_test.py setup` now always includes the files that hold quarantined rows; here 2 of the 6, one quarantined row each). Three more silver kill trials: 1 kill landed in the risky window (one file's rows written, no manifest row), 2 landed between files; every recovery matched production exactly, quarantine rows included (same rows, one manifest row per file, counts equal). That trial does not show which file the in-flight write belonged to, so it does not by itself prove the quarantine step was interrupted. The window between the silver write and the quarantine write is a few seconds and a cancel takes 30-38 s, so it cannot be hit by a kill; it was tested with a **constructed state instead**: after a normal scratch run, the 2 quarantine rows and the manifest rows of both quarantine files were deleted (silver rows kept: 13,432 rows, 0 quarantine, 0 manifest rows for those files, exactly what a crash in that window leaves), then a real recovery run: 13,434 rows in, 13,432 silver and 2 quarantine, no problems, quarantine rows and manifest counts identical to production. The crash state in that test is built by hand, not caused by a kill. Production counts were identical before and after.

- **Contract v4 (2026-10-17): ten columns added, 71 to 81, and one rule on the tag columns.** New: `checked`, `last_checked_t`, `additives_tags`, `ingredients_analysis_tags`, `nutrient_levels_tags`, `food_groups_tags`, `packaging_tags`, `origins_tags`, `product_quantity_unit`, `environmental_score_grade` (reasons, coverage and what was left out and why: the header of `contracts/silver.yml`). The rule `max_digit_run: 6` drops a tag with 7 or more digits in a row in every shape-checked tag column (58 tags in about 50 of 128,596 versions: bare barcodes and 10-digit numbers, which can be phone numbers). Proven on a scratch rebuild of all 128,598 bronze rows (`silver_v4_check.py`): all 67 unchanged old columns identical to production on every row (hashed ones included); the exceptions are the 2 old-format delta rows the legacy mapper now maps (13 nutrition columns) and the digit-run drops in the four older tag columns (categories 7 rows, labels 20, traces 10, allergens 0); the 10 new columns match bronze's raw JSON exactly; no contact-shaped or long-digit tag remains in any tag column; the drift monitor replayed on 16 days raises only the two known real alerts. **Not in production until the table swap** (silver is insert-only, so the old table cannot take the new columns: see the swap steps in the buildlog).
